VSVK Digitaal Platform: Doelarchitectuur

Strategisch advies voor de directie van VSVK over het creëren van een centraal enterprise dataplatform als fundament voor snelle applicatieontwikkeling.

Executive Summary: Van Losse Tool naar Enterprise Fundament

VSVK wil sneller nieuwe bedrijfsapplicaties kunnen ontwikkelen (o.a. calculatie, werkvoorbereiding, planning, urenregistratie, materieel en directie-dashboards). De huidige calculatietool bewijst de functionele meerwaarde, maar slaat data lokaal in de browser op.

Kernboodschap voor de directie:

Snelheid van applicatieontwikkeling kan alleen duurzaam worden behaald met een gestandaardiseerd centraal fundament (Single Source of Truth + API Gateway). Zonder dit fundament leidt elke nieuwe app tot gefragmenteerde data, foutieve calculaties en hoge beheerskosten.

Huidige Situatie (Baseline Prototype)

  • Data staat lokaal in browser localStorage (risico bij wissen/pc-wissel).
  • Artikelen, vestigingen en handtekeningen zitten opgeslagen in één 240 kB JSON-blob.
  • Geen centrale autorisatie of beveiligde koppeling met bedrijfsnetwerk.
  • Nummering en concurrency-checks zijn afhankelijk van een browserclient.

Doelsituatie (Enterprise Dataplatform)

  • Centrale interne PostgreSQL database met robuuste relationele kernentiteiten.
  • Centrale API Gateway voor autorisatie, rekenregels en unieke nummeruitgifte.
  • Frontends (web/tablet) kunnen razendsnel inhaken op kant-en-klare API-bouwstenen.
  • Volledig geïntegreerd met bestaande VSVK Microsoft 365 / Entra ID accounts.

Laag 1: PostgreSQL Datalaag

Waarom PostgreSQL 16+?

  • ACID-garanties: Foutloze nummeruitgifte en statuswijzigingen zonder dubbele records.
  • Hybride: Relationele kern gecombineerd met geïndexeerde JSONB voor calculatiedetails.
  • Open Source: Geen vendor lock-in; draait on-premise of in private cloud.
  • Audit Trail: Automatische vastlegging van wie wat wanneer wijzigt.

Laag 2: API Gateway (Node / .NET)

Verantwoordelijkheden:

  • Centrale Rekenregels: Calculatieformules, AK/W&R opslagen en btw staan op de server.
  • Nummer-sequencer: Concurrency-veilige uitgifte van calculatienummers (bijv. 2027-001).
  • OpenAPI / Swagger: Gestandaardiseerde endpoints voor alle frontends.
  • Security filter: Rate limiting, token-validatie en threat protection.

Laag 3: Applicatielaag

Snelheid door hergebruik:

  • Gedeelde DataStore SDK: Elke app gebruikt dezelfde client voor login en datakoppeling.
  • VSVK UI Stijl: Knoppen, tabellen, modals en headers zijn eenmalig ontworpen.
  • Multi-device: Geschikt voor desktop (calculators) én tablets/mobiel (uitvoerders buiten).

Enterprise Visie op Microservices: De Pragmatische Evolutie

Moet VSVK alles direct opsplitsen in 20 losse microservices? Nee. De bewezen best practice voor deze fase is de Modulaire Monoliet.

De Valkuil van Vroegtijdige Microservices

  • Explosie van operationele kosten: Direct behoefte aan Kubernetes, distributed tracing en complexe service meshes.
  • Verlies van transactie-integriteit: Cross-service transacties vereisen Saga-patronen en leiden snel tot dataverschillen tussen calculatie, offerte en planning.
  • Vertraging i.p.v. versnelling: Ontwikkelaars zijn meer tijd kwijt aan netwerkcontracten en containerdeployment dan aan bedrijfsfunctionaliteit.

De Oplossing: De Modulaire Monoliet

  • Eén deployment runtime & database: Eenvoudig te onderhouden, monitoren en back-uppen.
  • Strikte Bounded Contexts: Modules (Stamdata, Calculaties, Planning, Uren) zijn in de code strikt gescheiden.
  • Geen illegale dwarsverbanden: Modules praten uitsluitend via expliciete service-interfaces met elkaar.
  • Maximale ontwikkelsnelheid: Nieuwe apps kunnen direct in gebruik worden genomen.

Wanneer wél een microservice afsplitsen?

Omdat de domeinen logisch al strikt gescheiden zijn, kan VSVK in de toekomst zónder herontwerp een domein afsplitsen als zelfstandige microservice. Bijvoorbeeld bij een toekomstige IoT / Telemetrie module die tienduizenden GPS- en sensormeldingen per minuut van botsabsorbers en actiewagens ontvangt. De API Gateway schermt dit af: voor de gebruikers blijft de API identiek.

Security, Authenticatie & Autorisatie

Enterprise beveiliging gebaseerd op de standaarden van Microsoft 365, gecombineerd met strikte vestigingssegregatie.

1. Microsoft Entra ID (SSO & MFA)

Medewerkers loggen in met hun bestaande VSVK-account via OpenID Connect / OAuth 2.0.

  • Geen losse wachtwoorden in de applicatie.
  • MFA wordt automatisch centraal afgedwongen.
  • Bij uitdiensttreding direct uitgeschakeld in alle apps.
  • Kortlevende JWT-tokens bij elk verzoek.

2. Vestigingssegregatie (Data Scoping)

VSVK opereert vanuit 3 vestigingen: Pijnacker, Rilland en Wamel.

  • De API Gateway filtert queries automatisch op vestiging_id.
  • Calculators zien uitsluitend calculaties van hun eigen vestiging.
  • Directie en centrale administratie hebben overkoepelend inzicht.
  • Voorkomt overschrijffouten en datalekken.

3. AVG & Handtekeningenbeheer

In het prototype zit directie-handtekening SIG_PVK als ongecodeerde base64 in de code.

  • Handtekeningen verhuizen naar een beveiligde private object storage.
  • Alleen geautoriseerde backend-processen renderen handtekeningen in officiële PDF's.
  • Volledige encryptie in transit (TLS 1.3) en at rest (AES-256).

Non-Functional Requirements (NFR's) & Beheer

Randvoorwaarden om stabiliteit, snelheid en bedrijfscontinuïteit te garanderen.

Performance & Caching

  • API responstijden: < 100 ms voor reguliere data-opvragingen; < 300 ms voor complexe lijsten.
  • In-memory Caching: Artikelen en tarieven wijzigen zelden en worden in het servergeheugen gecachet.
  • Database Connection Pooling: Efficiënt hergebruik van databaseverbindingen bij piekdrukte.

Back-up & Disaster Recovery

  • RPO (Recovery Point Objective) < 1 uur: Dagelijkse volledige back-up + PostgreSQL Write-Ahead Logging (WAL) voor Point-in-Time Recovery.
  • RTO (Recovery Time Objective) < 2 uur: Volledig herstel op alternatieve infrastructuur binnen 2 uur bij een calamiteit.
  • Geen klantdata in Git: Strikte scheiding tussen code en bedrijfsdata.

Containerization (Docker)

Zowel de database, de API gateway als de webapplicaties draaien in lichtgewicht Docker-containers. Dit garandeert dat de ontwikkel-, test- en productieomgeving 100% identiek zijn.

CI/CD Pipeline (GitHub Actions)

Elke pull request wordt automatisch gecontroleerd op security-kwetsbaarheden, syntax en unit-tests. Goedgekeurde wijzigingen kunnen met één druk op de knop veilig worden uitgerold.

Gespreksagenda voor het Directieoverleg

Drie concrete strategische besluiten om voor te leggen aan de directietafel.

Besluit 1

Hostinglocatie

Voorstel: Private Cloud (Microsoft Azure Nederland / West-Europa) naadloos aangesloten op Microsoft 365.

Alternatief: On-premise server op hoofdkantoor Pijnacker met VPN-tunnels naar Rilland en Wamel.

Besluit 2

Authenticatiebeleid

Voorstel: Bestaande zakelijke Microsoft 365-accounts aanwijzen als de enige geautoriseerde inlog voor alle interne software (MFA verplicht).

Besluit 3

Prioriteit Volgende App

Voorstel: Akkoord op Fase 1 & 2 (Calculatie-app als live pilot). Vaststellen welke applicatie daarna prioriteit krijgt (Urenregistratie, Buitendienst Werkbonnen of Planning).

Business Case & Return on Investment (ROI)

Kwantitatieve Baten

  • 60% kortere bouwtijd: Vervolgapplicaties hoeven authenticatie, dataontsluiting en opmaak niet opnieuw te ontwikkelen.
  • Minder faalkosten: Geen verouderde artikeltarieven meer in offertes; tariefwijzigingen zijn in één seconde bedrijfsbreed actief.

Kwalitatieve Baten

  • Professionele audit trail: Direct inzicht in wie welke offerte heeft goedgekeurd.
  • AVG-compliance: Handtekeningen en persoonsgegevens veilig afgeschermd volgens de wet.
